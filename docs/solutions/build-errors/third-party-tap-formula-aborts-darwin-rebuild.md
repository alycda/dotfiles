# A third-party Homebrew tap's formula stopped loading and took the whole `darwin-rebuild` with it

## Problem

`nix-darwin`'s `homebrew` module runs `brew bundle` during activation, and `brew bundle` **loads every formula named in `brews`** — it has to, to decide whether the formula is installed and current. A formula is Ruby, evaluated by whatever Homebrew CLI is on the machine at that moment. So a third-party tap does not merely supply a package to this configuration; it supplies *code that Homebrew executes inside your activation*, and it can abort the activation by raising.

That is what happened. `darwin/modules/homebrew-personal.nix` and `darwin/modules/homebrew.nix` both listed `cirruslabs/cli/tart`. The tap's `tart.rb` declares macOS twice:

```ruby
  depends_on "cirruslabs/cli/softnet"
  depends_on :macos            # line 12 — bare
  ...
  depends_on :macos => :ventura  # line 22 — versioned
```

Homebrew *deprecated* that combination and then, in the 6.0 line, **disabled** it — a disabled API raises rather than warning. `softnet.rb:18` is broken identically. Every brew operation that touches either formula now fails, including the one nix-darwin performs on every switch.

**Nothing on this side changed.** No flake input moved, no module was edited. `homebrew.onActivation.autoUpdate = true` upgraded the Homebrew CLI, and the newly-strict CLI rejected a formula that had been sitting there working. A configuration can be bit-identical to yesterday's and still fail today, because part of what it evaluates is fetched at activation time from a repository nobody here controls.

**And `brew update` cannot fix it.** The tap's `origin/main` carries the same file — verified by fetching it. Upstream has known since 2026-06-10: issue #14, then five PRs (#15, #16, #17, #18, #19) proposing the `on_macos` block fix. Two are still open, three were closed unmerged. The reason they go nowhere is written at the top of the formula:

```ruby
# This file was generated by GoReleaser. DO NOT EDIT.
```

A PR against the tap would be overwritten by the next release. The fix has to land in tart's own GoReleaser configuration, which is a different repository and not something a downstream consumer can wait on with any confidence.

## Symptoms

`just _rebuild` (i.e. `darwin-rebuild switch --flake .#alyssa@shesfast`) printed a normal-looking brew bundle run and then stopped:

```
Using zoom
Warning: Formulae dependency graph sorting found a circular dependency:
  libtiff, webp
...
Using cirruslabs/cli/tart
Error: cirruslabs/cli/tart: Calling `depends_on :macos` with `depends_on macos:` is disabled! Use `depends_on :macos` with `depends_on macos:` inside an `on_macos` block instead.
Please report this issue to the cirruslabs/homebrew-cli tap (not Homebrew/* repositories), or even better, submit a PR to fix it:
  /opt/homebrew/Library/Taps/cirruslabs/homebrew-cli/tart.rb:22

error: recipe `_rebuild` failed on line 37 with exit code 1
```

Two things about this output are worth naming, because both cost time:

- **The `libtiff`/`webp` circular-dependency warning immediately above it is unrelated.** It is stale keg-tab metadata, it is a warning, and it carries its own remedy. It reads like context for the failure and is not.
- **The error points into `/opt/homebrew/Library/Taps/`, and the recipe line number it reports (`_rebuild`, line 37) is the `darwin-rebuild` invocation itself** — the two coordinates you are handed both point away from the cause. Nothing in this repo is at fault, and nothing in this repo can be edited to make that formula load.

Environment: Homebrew 6.0.22, macOS 15.7.4 (24G517), tart 2.32.1 installed from the tap.

## What Didn't Work

**1. `brew update`.** The instinct is that a tap is a git checkout and a stale one explains a stale-syntax error. It is not stale:

```sh
cd /opt/homebrew/Library/Taps/cirruslabs/homebrew-cli
git fetch origin && git show origin/main:tart.rb | grep -n 'depends_on'
#  11:  depends_on "cirruslabs/cli/softnet"
#  12:  depends_on :macos
#  22:  depends_on :macos => :ventura
```

Check the *remote* before concluding anything about a tap, exactly as you would check nixpkgs master before believing `nix flake update` will bump a lagging package.

**2. Patching the tap formula in place.** Deleting line 12 makes the error go away in about three seconds and is the obvious stopgap. Rejected: `onActivation.autoUpdate = true` means every switch runs `brew update`, which force-updates tap checkouts, so the patch is wiped on a schedule you did not choose — and its removal presents as the original failure returning at random. A fix that a routine background operation silently reverts is worse than no fix, because it costs the diagnosis twice.

**3. Waiting for upstream.** Ruled out on evidence, not impatience: five PRs over three months, three closed unmerged, and a `DO NOT EDIT` header explaining why merging one would not stick anyway.

**4. `pkgs.tart` from nixpkgs, unpinned — this is the one that looked done and was not.**

nixpkgs has tart, it is a plain `fetchurl` of upstream's release tarball rather than a source build, `allowUnfree` already covers its FSL-1.1-ALv2 licence, and the version there (2.36.0) was *newer* than the brewed 2.32.1. It builds:

```
$ NIXPKGS_ALLOW_UNFREE=1 nix build --impure nixpkgs#tart
/nix/store/dca8...-tart-2.36.0
```

And then it does not run:

```
$ .../bin/tart --version
dyld[19920]: Library not loaded: @rpath/libswiftCompatibilitySpan.dylib
  Reason: tried: '/usr/lib/swift/libswiftCompatibilitySpan.dylib' (no such file, not in dyld cache), ...
```

`libswiftCompatibilitySpan.dylib` is a Swift 6.2 back-deployment shim. On this machine it exists only under `/Library/Developer/CommandLineTools/usr/lib/swift-6.2/macosx/` — a *developer tools* path, not a runtime one. It ships in `/usr/lib/swift` on macOS 26; macOS 15 does not have it.

The first bisect attempt was wrong and is worth recording. Grepping `otool -L` for the library name reported that *every* release from 2.32.1 to 2.36.0 needed it — including the brewed 2.32.1 that was demonstrably running. The name is not the signal; the **linkage** is:

```
2.32.1  @rpath/libswiftCompatibilitySpan.dylib (..., weak)   ← dyld skips it when absent
2.36.0  @rpath/libswiftCompatibilitySpan.dylib (...)          ← dyld hard-fails when absent
```

Re-run checking for `weak` and the boundary is sharp:

| release | linkage | runs on macOS 15 |
|---|---|---|
| 2.32.1, 2.33.0, 2.33.1, **2.34.0** | weak | yes |
| 2.35.0, 2.36.0 | strong | **no** |

So a green `nix build` proved nothing here either. This repo already has the rule — *passing activation is not proof a tool works* (PR #37, lazydiff) — and this is the same rule one layer down: for a package that is a **prebuilt binary rather than a source build**, Nix verifies the tarball's hash and the install script. It never links, never loads, and therefore cannot tell you the binary will not start on this OS. Run the thing.

## Solution

Take tart from nixpkgs, and pin the version — two independent constraints, one file: `lib/tart.nix`.

```nix
pkgs:
pkgs.tart.overrideAttrs (_: {
  version = "2.34.0";
  src = pkgs.fetchurl {
    url = "https://github.com/openai/tart/releases/download/2.34.0/tart.tar.gz";
    hash = "sha256-yfFgn0lFJY7w7id91E3JcA1vBpeJoR5Dvn81sKZLMTU=";
  };
})
```

Imported by the two desktop profiles that need it — `home-manager/profiles/home.nix`, and the `lib.optionals stdenv.hostPlatform.isDarwin` block in `work.nix`, since that profile is also `alyssa@work-dev` on aarch64-linux:

```nix
      (import ../../lib/tart.nix pkgs)
```

A plain file returning a package, rather than an overlay: an overlay would have to be wired in `mkHome`, `darwin/configuration.nix` **and** the flake's devShells (the trap documented for `charm-nur`), which is three edits and a shared-`pkgs` coupling to buy nothing — nothing else consumes this and it is not a version bump anyone else should inherit.

`cirruslabs/cli/tart` came out of the `brews` list in *both* homebrew modules, and the now-unused `cirruslabs/cli` tap out of both `taps` lists. Checked first that nothing else came from that tap: every other formula in the personal module resolves to `homebrew/core` except `wishlist` (`charmbracelet/tap`).

Both machines were changed, not only the one that broke. `darwin/modules/homebrew.nix` (ditto) listed the same formula behind the same tap and would have failed on its next rebuild.

**The brewed copy has to be removed by hand before the switch.** `onActivation.cleanup = "zap"` will try to uninstall the formula that is no longer listed — and uninstalling loads the formula, which is the thing that fails. Order matters:

```sh
brew uninstall --ignore-dependencies --force tart softnet
brew untap cirruslabs/cli
darwin-rebuild switch --flake .#alyssa@shesfast
```

VM images live in `~/.tart` and are independent of the binary, so nothing is lost.

Verified: `lib/tart.nix` builds and `tart --version` prints `2.34.0`; `just lint` and `.github/scripts/eval-configurations.sh` pass across all seven configurations.

**What the pin costs, and when it comes out.** nixpkgs tracks tart HEAD, so this pin will drift and needs a conscious bump. Delete it — use plain `pkgs.tart` — once every machine is on macOS 26; that is the whole condition, and it is worth re-checking at the next macOS upgrade rather than at the next flake update.

**What the move costs.** softnet. nixpkgs' tart sets `enableSoftnet ? false` by default because `tart run --net-softnet` needs a setuid helper Nix cannot install, and nixpkgs' softnet is 0.7.1 against the tap's 0.19.0. Nothing here uses isolated VM networking — tart exists to verify a switch on a clean macOS image, which runs on default NAT — so this was accepted rather than worked around.

## Why This Works

`brew bundle` executes third-party Ruby during activation; `nix build` fetches a tarball whose hash is fixed in the expression. The failure mode being removed is not "tart was broken" but **"activation depended on code fetched at activation time from a repository with its own release cadence and its own idea of when to be correct."** nixpkgs is also third-party, but it is *pinned* — `flake.lock` says exactly which revision evaluates, and it changes when you run `nix flake update`, not when a background `brew update` decides.

This is the same reasoning that moved `crush` from nixpkgs to the vendor's flake, arriving from the other direction: there the point was that a pinned input can lag upstream, here that an unpinned one can move under you. Both reduce to *know which revision of someone else's code your switch is going to run, and make moving it an explicit act.*

The version pin works for a duller reason. A weak dynamic import is one dyld is permitted to leave unresolved; a strong one it is not. tart 2.35.0 changed that classification for a library that only exists on a newer OS, which makes 2.35.0+ a macOS 26 binary regardless of what its declared minimum says. 2.34.0 is the last release on the right side of that line.

## Prevention

1. **Treat every third-party tap in `brews`/`casks` as code that runs inside activation.** It can abort a switch entirely, on a machine where nothing local changed, at a time set by `autoUpdate`. That risk is proportional to how the tap is maintained: a GoReleaser-generated formula is fire-and-forget by construction — nobody re-runs it when Homebrew tightens an API, and PRs against it are overwritten by the next release.

2. **When a formula breaks, check `origin/main` before assuming a stale checkout**, and check the upstream issue tracker before assuming a fix is coming. `git show origin/main:<formula>.rb`, then `gh api repos/<tap>/pulls`. Closed-unmerged PRs proposing the exact fix are the signal to route around rather than wait.

3. **Prefer nixpkgs for anything nixpkgs actually has.** Homebrew is the documented fallback for what nixpkgs lacks. `nix eval --raw nixpkgs#<pkg>.version` costs seconds and is worth running against every entry in `brews` when one of them misbehaves.

4. **For a prebuilt-binary package, run it before believing it.** A green `nix build` of a `fetchurl`-based derivation verifies a hash, not an ABI. `<store-path>/bin/<prog> --version` is the whole test and it catches the entire class.

5. **When checking a dylib dependency, check the linkage, not the name.** `otool -L | grep <lib>` finds weak imports too and will tell you a working binary is broken:

   ```sh
   otool -L <binary> | grep CompatibilitySpan   # matches weak AND strong — useless alone
   otool -L <binary> | grep CompatibilitySpan | grep -q weak && echo "optional" || echo "required"
   ```

6. **A Swift binary that hard-links a `libswiftCompatibility*.dylib` is an OS-version constraint in disguise.** Those shims back-deploy new stdlib surface and live in `/usr/lib/swift` only from the OS release that introduced them. If one appears as a strong import after a version bump, the upstream project raised its floor whether or not it said so in release notes — bisect linkage across releases to find the last usable one.

7. **Removing an entry from `brews` is not enough when the formula is broken.** `cleanup = "zap"` uninstalls by loading the formula, so it fails the same way. Uninstall by hand first (`brew uninstall --ignore-dependencies --force`), then untap, then switch.
